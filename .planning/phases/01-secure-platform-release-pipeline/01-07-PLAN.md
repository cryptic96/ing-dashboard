## Phase Goal

ROADMAP goal (verbatim): A tagged release deploys itself to the homelab LXC through a pipeline that cannot leak secrets. The running platform (app, PostgreSQL, Prometheus and Grafana) is locked down and ready to hold financial data before any real bank data arrives.

This plan is the secrets slice: after it, the key ring that will protect bank consent tokens is encrypted at rest with a certificate from the env file, still decrypts after a restart and a redeploy, the app refuses to start in Production with unsafe configuration, and secrets provably stay out of logs, errors and metrics.

<objective>
Complete SEC-03 and OPS-05 by protecting the database-persisted Data Protection key ring with a PFX certificate whose path and password live only in the server-side env file (D-07), including the Linux-specific UnprotectKeysWithAnyCertificate registration. Enforce SEC-05 and D-09 at startup (socket-only, passwordless, runtime-role connection string). Implement SEC-06 redaction and prove it with sentinel tests covering empty, encoded and configuration-borne secrets.

Purpose: the canary proves the mechanism before the bank-sync phase stores real consent tokens with it.
Output: DataProtectionSetup, ProductionConfigurationValidator, LedgerConnectionStringRules, logging configuration, tests, env example update.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| env file → app process | Certificate password and path enter the process at startup |
| app → journald / Prometheus / HTTP responses | Anything logged, exported or returned may be read by more people than the secret's owner |
| database → key ring | Key material at rest in data_protection_keys |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Information Disclosure | data_protection_keys at rest | high | mitigate | ProtectKeysWithCertificate; test asserts encryptedSecret present and no plaintext master key |
| T-07-02 | Denial of Service | key ring unreadable after restart on Linux | high | mitigate | UnprotectKeysWithAnyCertificate with the same certificate; restart/redeploy test with a different content root |
| T-07-03 | Information Disclosure | secrets in logs | high | mitigate | Hosting diagnostics at Warning, no HTTP logging middleware, no EF sensitive logging; sentinel test over raw/URL-encoded/base64 forms |
| T-07-04 | Information Disclosure | secrets in exception messages and error responses | high | mitigate | Validator and setup name keys only; problem details without exception details outside Development; sentinel tests |
| T-07-05 | Information Disclosure | secrets in metric labels | medium | mitigate | Route-pattern labels only; sentinel test over /metrics |
| T-07-06 | Elevation of Privilege | app connecting as superuser or over TCP | high | mitigate | Production validator requires socket host, no password, ledger_runtime username |
| T-07-07 | Tampering | canary healed after key loss | medium | mitigate | Health check read-only; wrong-certificate test asserts Unhealthy and unchanged row |
| T-07-08 | Information Disclosure | certificate expiry | low | accept | Data Protection uses the certificate's key pair for unprotect regardless of expiry; a long validity self-signed certificate is generated by provisioning; rotation is supported later with UnprotectKeysWithAnyCertificate holding old and new certificates |

## Phase Goal

ROADMAP goal (verbatim; it is not written in user-story form, so no story is invented here): A tagged release deploys itself to the homelab LXC through a pipeline that cannot leak secrets. The running platform (app, PostgreSQL, Prometheus and Grafana) is locked down and ready to hold financial data before any real bank data arrives.

This plan is the Walking Skeleton tracer: the thinnest path through the app, the database roles and the release package. See `01-SKELETON.md` for the full spine and which plans complete it.

<assumption_delta_decision>
Primary noun: the single ledger LXC that hosts the app, PostgreSQL, Prometheus and Grafana as co-located systemd services.
Decision: no-change. The detector fired only on the word "alongside" in "runs the new version as a systemd service alongside PostgreSQL, Prometheus and Grafana", which describes co-located services, not a second variant of any identity model. No invariant test is needed.
</assumption_delta_decision>

<objective>
Stand up the Walking Skeleton: a .NET 10 solution whose ASP.NET Core host reads and writes one real row (the Data Protection canary) in PostgreSQL as the least-privilege runtime role, after the schema was created by the migrator role through the same bootstrap SQL the LXC will use; plus the release package (app + self-contained migration bundle + manifest + deploy tree) the pipeline and installer consume.

Implements D-08 (PostgreSQL via Npgsql), D-09/D-14 (socket-only, passwordless connection strings), D-10 (runtime/migrator/Grafana-reader roles, default privileges, reporting grants in the initial migration), D-11 (bootstrap SQL that provisioning runs as the postgres superuser over peer auth), D-13 (user's own local container via user-secrets, CI service container, no Testcontainers) and D-23 (health and metrics only on a loopback ops endpoint).

Purpose: prove the database and secrets architecture end-to-end on real PostgreSQL before any pipeline or LXC work builds on it.
Output: solution, projects, initial migration, bootstrap SQL, package script, and the integration tests that prove them.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → PostgreSQL | Runtime requests cross into the database; privileges must be enforced by roles, not app discipline |
| test harness → user's local container | Tests run with superuser credentials the user supplied; they create roles and throwaway databases |
| loopback ops endpoint ↔ network | /health and /metrics must never be reachable from outside the host |
| build script → release artifact | Everything in the zip later runs as root or as a service on the LXC |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Elevation of Privilege | ledger_runtime role | high | mitigate | Default privileges grant DML only; DatabaseRoleTests assert 42501 on CREATE/ALTER/DROP/CREATE SCHEMA; history table DML revoked in InitialCreate |
| T-01-02 | Information Disclosure | grafana_reader role | high | mitigate | Only USAGE on reporting plus default SELECT on reporting objects; tests assert 42501 on public tables and success only on a reporting view |
| T-01-03 | Denial of Service | Data Protection key ring | high | mitigate | Keys persisted in data_protection_keys, SetApplicationName("HouseholdLedger"), canary health check; restart/redeploy test with a different content root; canary never regenerated (test deletes keys and asserts Unhealthy + unchanged row) |
| T-01-04 | Information Disclosure | ops endpoint | high | mitigate | OpsEndpoint refuses non-loopback URLs at startup (unit tests); health and metrics filtered by connection local port via UseHealthChecks(path, port) and UseMetricServer(port) |

<objective>
Encrypt the reverse-proxy-to-application hop. Today Traefik forwards to the app over plain HTTP on port 5080, so passwords,
one-time codes, OAuth tokens, session cookies and every MCP answer cross the server network segment unencrypted. Other guests
on that segment are internet-facing; a compromised neighbour could ARP-spoof the hop and read or alter it. The host firewall
only limits who may connect, not who can intercept.

After this task the app serves HTTPS on 5080 with a long-lived self-signed certificate generated on the host, and Traefik
connects with HTTPS and trusts exactly that certificate (pinned through a serversTransport), so interception yields only
ciphertext and impersonating the app fails. Found by the pre-release code review (A-WR-06); operator decision: fix before release.
</objective>

<context>
- Ledger.Service/appsettings.json: Kestrel endpoint "Api" = http://0.0.0.0:5080 (REST API, sign-in pages, /mcp — everything
  Traefik reaches), "Ops" = http://127.0.0.1:5081 (health, metrics; loopback only — stays HTTP).
- deploy/bin/ledger-deploy (root-owned installer): installs a release, runs migrations, restarts, health-checks on the Ops port
  5081, and rolls back automatically UNLESS a migration ran. The next release contains a migration, so an app that fails to
  start after install would NOT roll back: the certificate must exist before the new release starts.
- deploy/provision.d/20-accounts.sh already generates /etc/ledger/dataprotection.pfx (root:ledger 0640) and renders
  /etc/ledger/ledger.env only when absent — follow its patterns (workdir, install -m/-o/-g, idempotence, logic tests).

  nftables rule admitting 5080/3000 only from the proxy address.
